Target profiles: the hook now understands what a coding agent reaches through cloud, Kubernetes, database, deployment and secret tools, and records it as Action Taxonomy 1.1 actions beside the command or MCP call itself.

- **Command-line tools** (`src/typed-targets.ts`): `aws`, `gcloud`, `az`, `kubectl`, `helm`, `terraform`/`tofu`, `wrangler`, `vercel`, `fly`, `gh`, the migration tools (prisma, drizzle-kit, rails/rake, alembic, flyway, knex, sequelize) and `eb`, `serverless`, `heroku`, `vault`, `doppler` and `op`, directly or through `npx`, `pnpm exec`, `uv run`, `python -m` or `bundle exec`. A known subcommand becomes `cloud.resource.create|modify|delete`, `k8s.apply|delete|exec`, `db.migrate`, `deploy.release`, `secret.write`, `iam.change` or (for `gh api`) `net.fetch`. Deterministic and pure; fixtures for every tool in `test/profiles/`.
- **MCP servers** (`src/mcp-profiles.ts`): `github` (pull requests, pushes, file writes), `filesystem`, `postgres`/`sqlite`/`mysql` (SQL classified, never recorded), `slack`, `playwright`/`puppeteer`, `fetch`, `linear` and `jira`. Any other server or tool stays the plain `mcp.tool.call` it was.
- **Wiring.** A derived action rides as its own intent (`derived: true` on the mapped action, `derived_from` in its params) beside the unchanged `shell.exec` or `mcp.tool.call`, in the same action group, so receipts for every existing command are unchanged and rules bind on the derived action type directly. The runtime evaluates a derived intent only under a policy that has a clause for its type; under a policy compiled before these types existed it is recorded (`not_evaluated`), so such a policy decides every call exactly as before. Derived intents get no observation operation of their own.
- **Rules.** Five new rules, all recording by default and never blocking until a person (`rules enforce <rule>`) or the workspace turns them on: `cloud-destructive` (cloud deletes, `k8s.delete`, `k8s.exec`), `production-deploy` (deployments to production, or whose environment the command does not show), `secret-write`, `iam-change` and `database-migrate` (migrations that go down or reset). Catalog classes H06–H10 (`MONITORED_HIGH`) name what each blocks; `classificationBlocks` is unchanged. A workspace rules document may set these rules and may leave them out (left out, they record); a document naming any other rule is still refused. `observe-targets` records cloud creates and changes, `k8s.apply`, `db.exec`, messages, work items and pull requests.
- **Behavior to know.** An MCP `push_files`, `create_or_update_file` or `delete_file` to a branch is now also a `git.push` to that branch, and a `filesystem` MCP read or write is a `file.read`/`file.write`, so `protect-branches`, `protect-write`, `protect-read` and Scopebond's own protection apply to them when those rules block. `gh api` is a `net.fetch` to `api.github.com` (or `--hostname`), so a workspace's allowed-sites rule covers it. An MCP database query is a `db.exec`, which `protect-remote-database` (when on) checks like a remote one.
