Block named MCP servers, hosts, programs and packages from the workspace's rules document. A workspace may send `blocked_services` (at most 500 entries of `{ kind: "mcp_server" | "host" | "cli" | "package", key }`); the hook now says it reads them (`x-scopebond-hook-capabilities` gains `service_rules`). The list is digested with the rules (`rules_digest` is the SHA-256 of the canonical JSON of `{ rules, blocked_services }` when the list is present), so a changed or malformed list refuses the document and the rules in force stay; a host key with a default port (`:80`, `:443`) is malformed, since a request's host never shows it. Each kind compiles into a policy clause (`blocked-mcp-servers`, `blocked-hosts`, `blocked-programs`, `blocked-packages`): an MCP call whose server name contains the blocked name as a word; a fetch by the coding agent's web-fetch tool (and a `gh api` call that changes something) to the blocked host, a port in the key must match (`curl`, `wget` and similar are recorded, not blocked); a shell command running the blocked program; or an install naming the blocked `manager:name` package. Every package an install names is checked (however many, also beside `-r` or `-e`; an unreadable spec is skipped), and an install whose named packages none can be read is denied while the workspace blocks any package. A denial says "Your workspace blocks the <kind> <key>" and is recorded like any rule block; a blocked package is recorded as that package's `package.install`, decided before its command. Without the list nothing changes.
